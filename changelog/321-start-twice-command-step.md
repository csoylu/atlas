## Fixed · #321 · A restart no longer cuts a command step already running in the engine, and a run killed right after its final answer ends Done

Two kill windows that failed the crash test in CI (#321):
- A second `workflows.start()` treated a command step this engine had already begun as one a stopped engine left. During the checkout (clone, fetch, worktree, before the process exists) it deleted every step worktree, so the step ended « couldn't run: can't check out … » and waited a minute for its automatic retry. Once the command was running, it killed its process group and stored the step as the command's own failure (« other exit · killed by SIGKILL »). Now a second `start()` only replaces the timer and the event subscription: steps and worktrees of the running engine are left alone, and `stop()` still kills them. At boot `start()` runs once, right after the HTTP server starts listening, so a « Run now » or webhook arriving in that gap could meet the window; it is tiny. A command was never run twice by this: the step is stored as running before the process starts, and a restart marks it cut off and never retries it by itself.
- A run killed after the agent's final answer was stored and before the run was closed stayed « interrupted » forever (a chat run is not resumed when no reply is owed, so nothing ever closed it) and its end was never reported to the dispatcher. At the next start such a run now ends Done, as if it had finished, with no second answer. A run that still owes a turn, or whose last message is a tool call, resumes as before. A run started with a kick message now stores the kick in the same transaction as the run, so a kill can no longer leave a run that never ran looking like one that answered.

No migration.
