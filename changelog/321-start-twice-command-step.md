## Fixed · #321 · A command step is no longer cut off, killed or left without its worktree when the workflow engine's start runs a second time

A second `workflows.start()` treated a command step this engine had already begun as one a stopped engine left. During the checkout (clone, fetch, worktree, before the process exists) it deleted every step worktree, so the step ended « couldn't run: can't check out … » and waited a minute for its automatic retry (the crash test failed on this in CI, #321). Once the command was running, it killed its process group and stored the step as the command's own failure (« other exit · killed by SIGKILL »). Now a second `start()` only replaces the timer and the event subscription: steps and worktrees of the running engine are left alone, and `stop()` still kills them. At boot `start()` runs once, right after the HTTP server starts listening, so a « Run now » or webhook arriving in that gap could meet the window; it is tiny, and the crash test's child engine, which calls `start()` late, hit it. A command was never run twice by this: the step is stored as running before the process starts, and a restart marks it cut off and never retries it by itself. No migration.
