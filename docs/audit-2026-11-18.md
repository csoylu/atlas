## 2. Method and legend

Expected behaviour comes from `docs/design.md` (§ numbers) and `CLAUDE.md`. "How" says what exercised it:

- **API** = Playwright `request` against the real engine (`e2e/tests/audit/api-*.spec.ts`), scripted model.
- **UI** = Playwright in Chrome against the built UI (`ui-screens.spec.ts`), with console/page errors and HTTP 5xx collected.
- **VT** = existing vitest file (read the list, ran it, did not re-derive its assertions).
- **SHOT** = `ui:check:fast` screenshot + OCR/layout check, and I looked at the images.
- Verdicts: **PASS**, **FAIL** (bug filed), **PARTIAL** (some of it exercised, said what), **BLOCKED** (cannot be tested here, said why).

Test IDs in `[brackets]` are the test titles in the spec files.

## 4. Bugs

### B1 (#121) — a card can be created or dragged into `running` by hand (P2 / medium-low)
Repro: `curl -X POST $ENGINE/api/cards -H 'content-type: application/json' -d '{"title":"x","status":"running"}'` → `201`, card sits in `running` with no run, no lease and nothing to resume it. Same with `PATCH /api/cards/:id {"status":"running"}`.
Expected (design §7): `running` is set by the dispatcher when a run starts; by hand it should be refused like other impossible moves (400/409 with a reason). Impact: a ghost "Running" card that never finishes and shows "An agent is working on it".
Test: `[K02b]` (`test.fail()` — remove when fixed).

### B2 (#122) — `claude_code` provider can still be created through the API (P3)
Repro: `POST /api/models {"id":"cc","provider":"claude_code","name":"x"}` → `201`. Design §5 and the comment at `packages/shared/src/index.ts:438` say the legacy CLI provider is removed (migration 0018): rows readable, never created. `ModelProvider` includes it in the create/update schema.
Impact: a user or agent can create a model that is not supported anymore. Test: `[M02]` (`test.fail()`).
**Fixed** in main ddcb9bb: POST/PATCH `/api/models` refuse `claude_code` with 400; `[M02]` no longer `test.fail()`. Still open (not in #122's scope): a legacy `claude_code` row is still *runnable* when the engine has `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` (`realProviders` in `engine/src/models.ts`); it only fails without them, which differs from "never runnable" in design §5.

### Lower-grade findings (not filed as bugs)
- **F2 (UI polish)**: Schedules at 390 px: the card's text column shrinks to ~80 px (title "Memory cleanup" wraps in 2 lines, prompt preview truncated "Weekly memory …") while Run now / Edit / Delete take the row. See `docs/audit-2026-11-18-shots/390-schedules.png`.
- **F3 (UI polish)**: Ticket modal at 390 px shows the status twice (a "Blocked" chip and a "Blocked" select) in the header; see `390-modal.png`.
- **F4 (tooling)**: `ui:check` reports "OCR can't read 'All' (.mem-chip): read 'AIl 3'" at 1440 on settings-memory-edit. The screenshot shows the chip "All 3" rendered correctly: OCR false positive (capital I / lowercase l in the sans font). Same family as earlier OCR noise.
- **F5 (tooling)**: `ui-check` has `MIN_FONT = 12` while the new type rules (#112, m94) say nothing under 13 px; the check will not catch 12 px text. Align it when #112 lands.

- **F6 (flaky test)**: `voiceLoop.test.ts` « stop »/« dur »/« hayır » barge-in (#53) failed in both full runs I did (also on the first, pre-rebase run), ~25 s, passes 15/15 alone (m72). Two out of two makes it more than rare noise under the full-suite load; it should get a looser timing or move out of the parallel set.

Test-harness limits (not product bugs): the e2e harness routes every model to the scripted provider, so provider errors (dead server) are only reachable by making the scripted model throw.
